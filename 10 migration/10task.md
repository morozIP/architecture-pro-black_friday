## Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

-----

### Задание 10.1. Определение критически важных сущностей для Cassandra

Cassandra оптимизирована для **высокой скорости записи**, **линейного горизонтального масштабирования** и **высокой доступности** с моделью **Eventual Consistency**.

**Выбранные критически важные сущности для миграции:**

1.  **Пользовательские сессии / Гостевые корзины (`carts` с TTL):**
      * **Обоснование:** Эти данные характеризуются **очень высокой частотой создания, чтения и обновления** (каждое добавление/удаление товара). Они **временные** (TTL) и **не критичны** с точки зрения строгой ACID-транзакционности. Небольшая задержка в согласовании данных корзины между репликами (например, пользователь добавил товар и увидел его через 100 мс) допустима и не приводит к прямым финансовым потерям. Cassandra эффективно обрабатывает такие временные данные, используя **TTL** для автоматической очистки, что снижает нагрузку на операции удаления.

**Сущности, которые остаются в MongoDB (для обеспечения транзакционности):**

  * **Заказы (`orders`) и Товары (`products`):** Требуют **строгой консистентности** и **атомарных транзакций** (создание заказа + списание остатков), что обеспечивается MongoDB.

### Задание 10.2. Концептуальная модель и ключи

Модель данных Cassandra **ориентирована на запросы (Query-Driven)**.

#### Концептуальная модель: История заказов по клиенту (`orders_by_customer`)

**Основной запрос:** Быстро получить текущую активную корзину по `user_id` или `session_id`.

| Поле | Тип Cassandra | Назначение ключа | Обоснование |
| :--- | :--- | :--- | :--- |
| **`cart_id`** | `uuid` | **Partition Key** | **Обеспечивает равномерное распределение** по узлам. Использование уникального `cart_id` как ключа распределения является **антипаттерном**, если нам нужно искать по `user_id`. |
| **`user_id`** | `uuid` | **Partition Key (если есть)** | Используется, если корзина принадлежит **залогиненному пользователю**. **Обеспечивает равномерное распределение** корзин пользователей. Запрос по `user_id` будет очень быстрым. |
| **`session_id`** | `text` | **Partition Key (если нет `user_id`)** | Используется для **гостевых корзин**. Аналогично, обеспечивает быстрый доступ. |
| **`status`** | `text` | **Clustering Key** | Корзины могут иметь статусы `active`, `ordered`, `abandoned`. Сортирует корзины пользователя, что позволяет быстро получить **активную** корзину. |
| `items` | `frozen<list<...>>` | Обычное поле | Список товаров в корзине. |
| `expires_at` | `timestamp` | Обычное поле + **TTL** | Время автоматического удаления корзины. |

**Для оптимизации запросов, создадим две "копии" данных (т.н. денормализация, или "Таблицы по запросам"):**

#### Таблица 1: `carts_by_user` (Для залогиненных)

**Основной запрос:** Получить активную корзину по `user_id`.

```cql
CREATE TABLE IF NOT EXISTS store_keyspace.carts_by_user (
    user_id uuid,
    status text,
    cart_id uuid,
    items frozen<list<frozen<map<text,text>>>>, /* Пример сложного типа */
    updated_at timestamp,
    expires_at timestamp,
    PRIMARY KEY (user_id, status)
) WITH default_time_to_live = 86400; -- TTL 24 часа для автоматической очистки
```

**Обоснование ключей:**

  * **Partition Key (`user_id`):** Все активные и неактивные корзины одного пользователя будут находиться на **одной партиции**. Это гарантирует, что запрос активной корзины (`WHERE status = 'active'`) будет быстрым, так как вся партиция читается с одного узла. Обеспечивает **равномерное распределение** нагрузки по клиентам.
  * **Clustering Key (`status`):** Сортировка по статусу ускоряет поиск.

#### Таблица 2: `carts_by_session` (Для гостей)

**Основной запрос:** Получить активную корзину по `session_id`.

```cql
CREATE TABLE IF NOT EXISTS store_keyspace.carts_by_session (
    session_id text,
    status text,
    cart_id uuid,
    items frozen<list<frozen<map<text,text>>>>,
    updated_at timestamp,
    expires_at timestamp,
    PRIMARY KEY (session_id, status)
) WITH default_time_to_live = 86400; -- TTL 24 часа для автоматической очистки
```

**Обоснование ключей:**

  * **Partition Key (`session_id`):** Аналогично `user_id`, обеспечивает быстрый доступ по сессии и равномерное распределение гостевых корзин.

### Задание 10.3. Стратегии обеспечения целостности данных

Для **Корзин/Сессий** ключевым является **Low Latency** (низкая задержка) для частых операций чтения/записи/обновления. **Eventual Consistency** здесь приемлема.

| Стратегия | Применение | Сущности | Обоснование выбора |
| :--- | :--- | :--- | :--- |
| **Hinted Handoff** (H.H.) | **При записи (Write):** Если узел-реплика временно недоступен, данные записываются с "подсказкой" для последующей доставки. | **`carts_by_user`**, **`carts_by_session`** | Обеспечивает **минимальную задержку записи** и **высокую доступность**. Если узел ненадолго упал, запись (например, добавление товара в корзину) не блокируется. |
| **Read Repair** (R.R.) | **При чтении (Read):** Если при чтении обнаруживается расхождение, устаревшие реплики обновляются в фоновом режиме. | **`carts_by_user`**, **`carts_by_session`** | **Улучшает согласованность при чтении**. Подходит для данных корзин, которые часто читаются. Небольшое увеличение **Latency** чтения приемлемо для устранения расхождений. |
| **Anti-Entropy Repair** (A.E.R.) | **Фоновое обслуживание (nodetool repair):** Регулярный процесс для полной синхронизации всех расхождений. | **Все сущности** | **Максимальная гарантия согласованности**. Запускается в непиковое время (например, ночью) для устранения всех пропущенных расхождений. |

**Уровень согласованности (Consistency Level - CL):**

  * Для **записи** и **чтения** корзин рекомендуется использовать `CL=LOCAL_QUORUM` (или просто `QUORUM` в зависимости от топологии). Это гарантирует, что большинство реплик в локальном датацентре подтвердят операцию. Это обеспечивает хороший баланс между **скоростью (Latency)** и **надежностью** данных корзины.
