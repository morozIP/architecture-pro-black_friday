## Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

-----

### Задание 10.1. Определение критически важных сущностей для Cassandra

Cassandra, как распределенная база данных без лидера, оптимизирована для **высокой скорости записи**, **линейного горизонтального масштабирования** и **высокой доступности** (модель eventual consistency). Она идеально подходит для рабочих нагрузок, где важна скорость записи и поиска по ключу, а не сложные транзакции.

**Выбранные критически важные сущности для миграции:**

1.  **Заказы и История заказов (`orders`):**

      * **Обоснование:** Заказы представляют собой **события**, которые после создания изменяются редко (в основном, обновляется только статус). Во время пиковой нагрузки (50 000 запросов/сек.) критически важна **высокая пропускная способность записи** и **быстрый поиск всей истории заказов** конкретного клиента. Cassandra обеспечивает эти требования без дорогостоящего перераспределения данных (решардинга) при добавлении узлов.

2.  **Пользовательские сессии / Гостевые корзины (`carts` с TTL):**

      * **Обоснование:** Эти данные характеризуются **очень высокой частотой создания/обновления** и **коротким сроком жизни (TTL)**. Cassandra эффективно обрабатывает такие временные данные, используя TTL для автоматической очистки, что снижает нагрузку на операции удаления.

### Задание 10.2. Концептуальная модель и ключи

Модель данных Cassandra **ориентирована на запросы (Query-Driven)**. Ключевая задача — обеспечить **равномерное распределение данных** и **быстрый доступ** путем использования ключей партиции.

#### Концептуальная модель: История заказов по клиенту (`orders_by_customer`)

**Основной запрос:** Быстро получить все заказы для конкретного клиента (для отображения истории).

| Поле | Тип Cassandra | Назначение ключа | Обоснование |
| :--- | :--- | :--- | :--- |
| **`customer_id`** | `uuid` | **Partition Key** | **Обеспечивает равномерное распределение** клиентов по узлам (шардам). Все записи заказов одного клиента находятся в одной **партиции** на одном узле, что гарантирует **быстрое чтение** всей истории за один запрос к узлу. |
| **`order_date`** | `timestamp` | **Clustering Key (DESC)** | **Сортирует** заказы внутри партиции по дате в обратном порядке (от новых к старым). Оптимизирует наиболее частый запрос: "показать последние заказы". |
| **`order_id`** | `uuid` | **Clustering Key** | Обеспечивает уникальность записей, даже если два заказа были оформлены в ту же миллисекунду. |
| `status` | `text` | Обычное поле | |
| `total_amount` | `decimal` | Обычное поле | |

**Обоснование выбора ключей:**

1.  **Partition Key (`customer_id`):** Выбор `customer_id` гарантирует, что при добавлении новых узлов в кластер данные (заказы) **не будут полностью перераспределяться** (нет решардинга). Распределение основано на хэше ключа, который равномерно распределяется по виртуальным узлам (vNodes), что и обеспечивает быстрое масштабирование. Риск **"горячей" партиции** минимален, так как даже самый активный клиент не сможет создать достаточное количество заказов в единицу времени, чтобы перегрузить узел.

**Пример создания таблицы (CQL):**

```cql
CREATE TABLE IF NOT EXISTS store_keyspace.orders_by_customer (
    customer_id uuid,
    order_date timestamp,
    order_id uuid,
    status text,
    total_amount decimal,
    geozone text,
    PRIMARY KEY (customer_id, order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC);
```

### Задание 10.3. Стратегии обеспечения целостности данных

В Cassandra целостность данных поддерживается за счет стратегий, которые компенсируют ее архитектуру без лидера и eventual consistency.

| Стратегия | Применение | Сущности | Обоснование выбора |
| :--- | :--- | :--- | :--- |
| **Hinted Handoff** (H.H.) | **При записи (Write):** Если узел-реплика временно недоступен, координирующий узел записывает "подсказку" (Hint), чтобы передать данные недоступному узлу, когда тот восстановится. | **`orders_by_customer`** | Обеспечивает **минимальную задержку записи (Low Latency)** и **высокую доступность** во время пиковых нагрузок. Если узел ненадолго упал, запись не блокируется. |
| **Read Repair** (R.R.) | **При чтении (Read):** Если при чтении с нескольких реплик обнаруживается расхождение, координатор обновляет устаревшие реплики в фоновом режиме. | **`orders_by_customer`** | **Улучшает согласованность при чтении** без запуска полного цикла Repair. Подходит для часто читаемых данных, где небольшое увеличение **Latency** чтения приемлемо для устранения расхождений. |
| **Anti-Entropy Repair** (A.E.R.) | **Фоновое обслуживание:** Регулярный процесс (например, `nodetool repair`), который сравнивает хеши данных (Merkle Trees) между всеми репликами и синхронизирует все расхождения. | **Все сущности** | **Максимальная гарантия согласованности (Final Consistency).** Запускается вне пиковых нагрузок, поскольку является ресурсоемким. Устраняет расхождения, которые могли быть пропущены H.H. и R.R. |

**Обоснование выбора стратегии и компромиссов:**

  * **Компромисс:** Использование **Hinted Handoff** и **Read Repair** позволяет достичь баланса между низкой задержкой **записи** (важно в пик "Черной пятницы") и достаточным уровнем согласованности **чтения**.
  * **Уровень согласованности (Consistency Level - CL):**
      * Для **записи** и **чтения** `orders_by_customer` рекомендуется использовать `CL=QUORUM`. Это гарантирует, что большинство реплик подтвердят запись/чтение, обеспечивая модель **Read-Your-Writes** (вы всегда увидите данные, которые только что записали) и хороший уровень надежности, не жертвуя при этом доступностью, как при использовании `CL=ALL`.
