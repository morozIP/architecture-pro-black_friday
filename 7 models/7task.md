## Задание 7. Проектирование схем коллекций для шардирования данных

### 1\. Коллекция `orders` (Заказы)

| Атрибут | Описание | Тип данных (MongoDB) |
| :--- | :--- | :--- |
| `_id` | Уникальный идентификатор заказа | `ObjectId` |
| `customer_id` | Идентификатор клиента | `int` / `string` |
| `order_date` | Дата и время оформления заказа | `Date` |
| `items` | Список заказанных товаров (вложенный массив) | `Array of documents` |
| `status` | Статус заказа | `string` |
| `total_amount` | Общая сумма заказа | `decimal128` |
| `geozone` | Геозона заказа | `string` |

-----

#### Кандидаты на шард-ключ:

  * `_id` (не подходит, так как ObjectId генерируется по времени и не способствует равномерному распределению по клиентам или дате).
  * **`customer_id`**: Обеспечивает, что вся история заказов одного пользователя будет находиться на одном шарде (т. н. **colocation**).
  * **`{customer_id, order_date}`** (Compound key): Улучшает распределение, но усложняет.
  * **`geozone`**: Может привести к **"горячим" шардам**, если в одной зоне заказов намного больше (например, Москва).

#### 🛡️ Выбранная стратегия и шард-ключ:

| Стратегия | Шард-ключ | Обоснование |
| :--- | :--- | :--- |
| **Hashed Sharding (Хэширование)** | **`customer_id`** | **Хэширование** по `customer_id` **равномерно** распределяет пользователей по шардам, избегая "горячих" шардов, связанных с географией или датой. Это подходит для основного паттерна **"Поиск истории заказов конкретного пользователя"** (`customer_id` в запросе). Все заказы пользователя будут на одном шарде, что обеспечивает высокую производительность для этого запроса. Также это помогает быстро создать заказ (запись). |

#### Пример команды:

```bash
sh.enableSharding("somedb")
sh.shardCollection("somedb.orders", { "customer_id": "hashed" })
```

### 2\. Коллекция `products` (Товары)

| Атрибут | Описание | Тип данных (MongoDB) |
| :--- | :--- | :--- |
| `_id` | Уникальный идентификатор товара | `ObjectId` |
| `name` | Наименование | `string` |
| `category` | Категория товара | `string` |
| `price` | Цена | `decimal128` |
| `stock` | Остаток товара в каждой геозоне (вложенный массив или Map) | `Array of documents` / `Map` |
| `attributes` | Дополнительные атрибуты (цвет, размер) | `document` |

-----

#### Кандидаты на шард-ключ:

  * **`_id`**: Хорошо распределяет, но не поддерживает запросы по категориям или остаткам.
  * **`category`**: Поддерживает **"Поиск товаров по категориям"**, но может вызвать **"горячий" шард**, если одна категория (например, "Электроника") намного популярнее (как описано в Задании 8).
  * **`{category, _id}`** (Compound key): Улучшает распределение.

#### Выбранная стратегия и шард-ключ:

| Стратегия | Шард-ключ | Обоснование |
| :--- | :--- | :--- |
| **Range Sharding (По диапазону)** | **`{category: 1, _id: 1}`** | Используя **составной ключ** по **категории и идентификатору**, мы группируем товары по категориям, что ускоряет основной запрос **"Поиск товаров по категориям и фильтрация"**. **Range Sharding** позволяет создавать **зоны (Zones)** для управления распределением данных. Мы можем выделить популярные категории на **большее количество шардов** (например, "Электроника" на 2 шарда), а менее популярные — на 1 шард, чтобы избежать "горячих" шардов. Это также локализует обновления остатков (`stock`) на том же шарде, что и сам товар. |

#### 📝 Пример команды:

```bash
sh.enableSharding("somedb")
sh.shardCollection("somedb.products", { "category": 1, "_id": 1 })

// Пример создания зоны для популярной категории "Electronics"
sh.addShardTag("shard1", "ElectronicsZone")
sh.addShardTag("shard2", "ElectronicsZone")
sh.addTagRange( "somedb.products", { "category": "Electronics", "_id": MinKey }, { "category": "Electronics", "_id": MaxKey }, "ElectronicsZone" )
```

### 3\. Коллекция `carts` (Корзины)

| Атрибут | Описание | Тип данных (MongoDB) |
| :--- | :--- | :--- |
| `_id` | Уникальный идентификатор корзины | `ObjectId` |
| `user_id` | Идентификатор пользователя | `int` / `string` |
| `session_id` | Идентификатор сессии для гостей | `string` |
| `items` | Список товаров в корзине | `Array of documents` |
| `status` | Статус корзины | `string` |
| `created_at` | Дата и время создания | `Date` |
| `updated_at` | Дата и время последнего обновления | `Date` |
| `expires_at` | Время удаления (TTL) | `Date` |

-----

#### Кандидаты на шард-ключ:

  * **`_id`**: Хорошо распределяет, но не поддерживает запросы по пользователю/сессии.
  * **`user_id` / `session_id`**: Локализует корзину на одном шарде.
  * **`{user_id, session_id}`**: Составной ключ, может быть разреженным.

#### Выбранная стратегия и шард-ключ:

| Стратегия | Шард-ключ | Обоснование |
| :--- | :--- | :--- |
| **Hashed Sharding (Хэширование)** | **`_id`** | **Хэширование** по **`_id`** обеспечивает **максимально равномерное** распределение данных. Это важно, так как корзины — это сущность с **очень высокой частотой создания и изменения**, и важно избежать перегрузки какого-либо шарда. Основные операции — **"Получение текущей корзины по фильтру { session\_id, status:"active" } или { user\_id, status:"active" }"** — в любом случае будут использовать **индексы** по `user_id` и `session_id` для поиска, а равномерное распределение записей по шардам минимизирует риски "горячих" шардов, связанных с активностью отдельных пользователей/сессий. |

#### Пример команды:

```bash
sh.enableSharding("somedb")
sh.shardCollection("somedb.carts", { "_id": "hashed" })
```
