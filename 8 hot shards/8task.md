## Задание 8. Выявление и устранение «горячих» шардов

Для решения проблемы с «горячими» шардами, вызванными популярностью категории «Электроника», необходимо внедрить систему мониторинга и разработать механизмы автоматического или ручного перераспределения данных.

-----

### 1\. Метрики для отслеживания состояния шардов

Чтобы выявить дисбаланс нагрузки, нужно отслеживать как общие метрики кластера, так и специфические метрики каждого шарда.

| Метрика | Описание | Инструменты/Источник | Причина перегрузки |
| :--- | :--- | :--- | :--- |
| **Операции (OPs) в секунду** | Количество команд чтения/записи (CRUD) на шарде. | `mongostat`, `db.serverStatus().opcounters` | Неравномерное распределение частоты запросов. |
| **Использование CPU** | Процент загрузки процессора на инстансах `mongod`. | Системный мониторинг (Prometheus/Grafana) | Слишком много сложных запросов или высокая частота OPs на конкретном шарде. |
| **Использование Disk I/O** | Скорость чтения/записи на диск (операции ввода-вывода). | Системный мониторинг | Шард обрабатывает большой объем данных, например, при сканировании индексов или частых обновлениях. |
| **Размер данных** | Объем хранимых данных на шарде (после сжатия). | `db.serverStatus().wiredTiger.data_sizes` | Неравномерное распределение данных (Data Skew). |
| **Размер очереди (Queue size)** | Количество запросов, ожидающих обработки. | `db.serverStatus().network.numRequestsInQueue` | Индикатор того, что шард не справляется с текущим потоком запросов. |
| **Задержка (Latency)** | Среднее время ответа на запросы на шарде. | `db.serverStatus().oplatencies` | Основной симптом "горячего" шарда. |

**Сигналы о «горячем» шарде:**

  * **Высокое** количество OPs, CPU и I/O на одном шарде по сравнению с другими.
  * **Значительно** более высокая задержка (Latency) на этом же шарде.

-----

### 2\. Механизмы автоматического перераспределения данных (Устранение дисбаланса)

Поскольку проблема вызвана неравномерной нагрузкой по категории (`category: "Electronics"`), необходимо использовать возможности, которые предоставляет **Range-Based Sharding** (который был предложен в Задании 7 для коллекции `products`).

#### 1\. Зонирование (Tag-Aware Sharding)

Это основной механизм для решения проблемы "горячих" категорий. Он позволяет вручную назначать диапазоны ключей конкретным шардам.

**Суть:** Если категория "Электроника" слишком популярна, можно разделить её данные между двумя или более шардами.

1.  **Создание зон (Tags):** Назначаем теги новым или менее загруженным шардам.
    ```javascript
    sh.addShardTag("shard3", "HighTrafficZone")
    sh.addShardTag("shard4", "HighTrafficZone")
    ```
2.  **Назначение диапазона ключей:** Определяем диапазон для "Электроники" и назначаем его этим шардам.
    ```javascript
    // Отключаем балансировщик, чтобы вручную настроить диапазоны
    sh.stopBalancer()

    // Назначаем диапазон "Electronics" на шарды с тегом "HighTrafficZone"
    sh.addTagRange(
        "somedb.products",
        { "category": "Electronics", "_id": MinKey },
        { "category": "Electronics", "_id": MaxKey },
        "HighTrafficZone"
    )

    // Включаем балансировщик. Он начнет перемещать чанки категории "Electronics"
    // только на шарды с тегом "HighTrafficZone" (shard3, shard4).
    sh.startBalancer()
    ```

#### 2\. Манипуляции с размером чанка (Chunk Size Manipulation)

Размер чанка по умолчанию составляет 64 МБ. Если "горячий" шард перегружен, можно временно уменьшить размер чанка для проблемной коллекции, чтобы балансировщик мог быстрее разделить большие чанки и перераспределить их.

```javascript
// Уменьшение размера чанка для коллекции products (с 64 МБ до, например, 32 МБ)
use config
db.settings.updateOne(
   { _id: "chunksize" },
   { $set: { value: 32 } }
)
```

После уменьшения чанки категории "Электроника" будут разделены на более мелкие, и балансировщик сможет более равномерно распределить их по назначенным шардам. После устранения дисбаланса размер чанка стоит вернуть к значению по умолчанию.

#### 3\. Переход на Hashed Sharding для высоконагруженных коллекций

Если **Range Sharding** постоянно приводит к дисбалансу из-за непредсказуемой популярности категорий, может потребоваться пересмотреть шард-ключ.

Для коллекций, где важна только равномерная запись (например, `carts`), **Hashed Sharding** (Хэширование) обеспечивает почти идеальное распределение нагрузки и данных, так как ключ распределяется по всему числовому диапазону.

**Действия:**

  * Оценить, возможен ли переход на `Hashed Sharding` для `products` (если отказ от локализации по категории приемлем).
  * Для коллекции `products` (с Range Sharding по `{category, _id}`) рассмотреть возможность использования **Hashed Sharding** по полю, которое обеспечивает уникальность и равномерное распределение, например, по `_id` (хотя это затруднит запросы по диапазону категорий).

**Важно:** Использование **Balancing Policy** (встроенного балансировщика) гарантирует, что MongoDB автоматически перераспределяет чанки между шардами, чтобы выровнять их количество. Зонирование — это ручной инструмент, который направляет работу балансировщика.
